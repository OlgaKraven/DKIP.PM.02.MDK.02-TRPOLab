    Лабораторная работа №3 - Построение архитектуры программного средства

    1. Теория

    1.0. Цель работы

    Целью лабораторной работы является освоение принципов архитектурного проектирования программного средства с использованием модели C4, включая формирование контекстного, контейнерного и компонентного представлений системы, определение границ ответственности, способов взаимодействия компонентов и обоснование выбранных архитектурных решений.

    1.1. Понятие архитектуры программного средства

    Архитектура программного средства (ПС) — это совокупность структурных решений о компонентах системы, связях между ними, принципах организации, паттернах взаимодействия и ограничениях, определяющих её качество, расширяемость, эффективность и жизненный цикл.

    Архитектура определяет:

    • Что делает система (функциональные требования).
    • Как она должна работать (нефункциональные требования: производительность, надёжность, безопасность, масштабируемость).
    • Какие элементы и модули должны существовать в системе.
    • Каким образом эти элементы взаимодействуют.

    Архитектор фиксирует ключевые решения в виде:

    • архитектурных стилей,
    • диаграмм,
    • ограничений,
    • документированных компромиссов.

    1.2. Цели построения архитектуры

    Построение архитектуры направлено на:

    1. Удовлетворение требований — создание структуры, способной обеспечить выполнение всех функциональных и нефункциональных требований.
    2. Управление сложностью — разделение системы на управляемые компоненты.
    3. Повышение устойчивости системы (robustness) — обеспечение отказоустойчивости и предсказуемости.
    4. Масштабируемость — возможность развития ПС без полного переписывания.
    5. Минимизация рисков — выявление архитектурных слабостей до начала разработки.
    6. Оптимизацию стоимости владения (TCO) — снижение затрат на поддержку и развитие.

    1.3. Компоненты архитектуры программного средства

    1.3.1. Функциональная архитектура

    Определяет:

    • основные функции и сценарии использования;
    • модули, отвечающие за реализацию пользовательских требований;
    • границы модулей (bounded contexts);
    • основные потоки данных.

    Используемые артефакты:

    • диаграммы вариантов использования (Use Case);
    • сценарии взаимодействия (Sequence);
    • контекстная диаграмма.

    1.3.2. Логическая архитектура

    Описывает разбиение системы на подсистемы и их ответственность.

    Типичные уровни:

    • уровень представления (UI/UX);
    • уровень бизнес-логики;
    • уровень доступа к данным.

    Логическая архитектура не привязана к конкретным технологиям — это модель сущностей и правил.

    1.3.3. Физическая архитектура

    Определяет размещение программных компонентов на:

    • серверах,
    • контейнерах,
    • базах данных,
    • сетевой инфраструктуре.

    Для визуализации используются:

    • диаграммы развёртывания (Deployment),
    • схемы инфраструктуры.

    1.3.4. Архитектура данных

    Включает:

    • модели данных;
    • схемы БД;
    • форматы хранения и передачи данных (JSON, XML, Protobuf);
    • правила валидации;
    • стратегии миграций.

    1.3.5. Интеграционная архитектура

    Описывает взаимодействие между компонентами и внешними системами.

    Может включать:

    • REST / gRPC API контракты,
    • очереди сообщений (RabbitMQ, Kafka),
    • события и подписчики (event-driven),
    • адаптеры внешних сервисов.

    1.3.6. Архитектура безопасности

    Фиксирует:

    • модели доступа (RBAC/ABAC),
    • аутентификацию и авторизацию (OAuth2, JWT),
    • протоколы шифрования (TLS),
    • защиту данных и логирование.

    1.3.7. Архитектура эксплуатации (DevOps)

    Формирует требования и решения по:

    • CI/CD pipeline,
    • сборке и доставке артефактов,
    • мониторингу и логированию,
    • контейнеризации,
    • оркестрации (Kubernetes, Docker Swarm).

    1.4. Архитектурные стили

    1.4.1. Монолитная архитектура

    Единый исполняемый модуль, содержащий все компоненты.

    Преимущества:

    • простота разработки;
    • единое деплоивание.

    Недостатки:

    • сложность масштабирования;
    • ограниченная гибкость.

    1.4.2. Клиент-серверная архитектура

    Кунстный раздел между клиентской частью и серверной частью.

    1.4.3. Слоистая (Layered) архитектура

    Одна из самых распространённых моделей:

    • Presentation Layer
    • Business Logic Layer
    • Data Access Layer
    • Infrastructure Layer

    Плюсы:

    • чёткое разделение ответственности;
    • управляемость модульностью.

    1.4.4. Микросервисная архитектура

    Система состоит из независимых сервисов.

    Преимущества:

    • гибкость;
    • независимость команд;
    • масштабирование отдельных частей.

    Недостатки:

    • сложность инфраструктуры;
    • распределённые транзакции.

    1.4.5. Service-Oriented Architecture (SOA)

    Сервисы связаны через шину (ESB), обеспечивающую централизованную интеграцию.

    1.4.6. Event-driven Architecture

    Система реагирует на события; используется pub/sub-модель.

    1.5. Архитектурные паттерны

    1. MVC / MVVM / MVP — разделение представления, логики и моделей.
    2. Repository — абстракция работы с данными.
    3. Factory / Singleton / Observer — классические шаблоны ООП.
    4. Gateway / Adapter — стандартизация доступа к внешним системам.
    5. CQRS — разделение операций чтения и записи.
    6. Saga / Orchestration — координация процессов в распределённых системах.

    1.6. Требования, влияющие на архитектуру

    1.6.1. Функциональные требования

    Определяют архитектурные границы модулей и потоков данных.

    1.6.2. Нефункциональные требования

    Существенно влияют на выбор технологий.

    Типы NFR:

    • производительность (latency, throughput);
    • масштабируемость;
    • отказоустойчивость;
    • безопасность;
    • удобство поддержки (Maintainability);
    • переносимость;
    • модульность.

    Архитектура должна обеспечивать выполнение NFR на уровне проектных решений.

    1.7. Технологические решения и ограничения

    При проектировании фиксируются:

    1. Язык программирования.
    2. Фреймворки.
    3. Библиотеки.
    4. Базы данных.
    5. Инструменты DevOps.
    6. Интеграционные протоколы.
    7. Платформа развёртывания (cloud/on-premise).

    Эти решения должны быть согласованы с требованиями, квалификацией команды и бюджетом.

    1.8. Документирование архитектуры

    Архитектурная документация включает:

    • Диаграмму контекстов — уровень С0 (C4 model).
    • Диаграмму контейнеров — С1.
    • Диаграмму компонентов — С2.
    • Диаграмму классов / модулей — С3.
    • Диаграмму развёртывания.
    • ADR (Architectural Decision Records) — фиксация ключевых решений.
    • API-контракты.
    • Руководство по архитектуре.

    1.9. Процесс построения архитектуры

    Процесс включает восемь этапов, от анализа требований до архитектурного аудита.

    Шаг 1. Анализ требований

    Сбор FR и NFR, анализ рисков и ограничений.

    Шаг 2. Выбор архитектурного стиля

    Монолит, слои, микросервисы, события и др.

    Шаг 3. Проектирование логической структуры

    Определение подсистем, модулей, интерфейсов.

    Шаг 4. Проектирование данных

    ER-диаграммы, схемы API, форматы.

    Шаг 5. Проектирование интеграций

    Адаптеры, API, события.

    Шаг 6. Разработка прототипов (Proof of Concept)

    Проверка выбранных технологий.

    Шаг 7. Документирование решений

    1.10. Ключевые качества хорошей архитектуры

    • Простота и ясность.

    1.11. Создание диаграммы C4

    1.11.1. Общие сведения о C4 Model

    C4 Model — это современный стандарт визуального описания архитектуры программного обеспечения, предложенный Саймоном Брауном. Название C4 означает четыре уровня абстракции:

    1. Context (Контекст) — кто взаимодействует с системой и в каком окружении она существует.
    2. Container (Контейнеры) — крупные участки системы: приложения, API, БД, очереди сообщений.
    3. Component (Компоненты) — внутренние части контейнеров: сервисы, модули, классы бизнес-логики.
    4. Code (Код/классы) — отдельные классы и структуры (используется редко).

    C4 позволяет:

    • описывать архитектуру сверху вниз;
    • фиксировать ответственность каждого элемента;
    • показывать структурные связи;
    • документировать систему независимо от конкретных технологий.

    1.11.2. Что такое компонент в C4

    Компонент в C4-модели — это логически обособленная часть контейнера, отвечающая за конкретный кусок функциональности.

    Это не класс и не исходный файл, а архитектурная единица, объединяющая:

    • ответственность (responsibility);
    • функциональность (capability);
    • интерфейсы (API/методы);
    • взаимодействие с другими компонентами;
    • зависимость от репозиториев, адаптеров, внешних сервисов и т. д.

    Примеры компонентов:

    • OrderController, AuthController;
    • PaymentService, NotificationService;
    • UserRepository, ProductRepository;
    • EncryptionProvider;
    • ExternalCRMAdapter;
    • EventPublisher.

    Основные элементы C4

    Пользователи

    Персоны и внешние акторы.

    Связи

    Штриховые линии с подписями.

    Программная система

    Блок, отображающий разрабатываемое решение.

    Контейнер

    Веб-приложение, API-сервер, БД, очередь сообщений, мобильное приложение.

    1.11.3. Основной принцип выделения компонентов

    Компонент должен быть выделен, если:

    1. Он выполняет уникальную бизнес-роль. Например: «Создать заказ», «Рассчитать тариф», «Проверить доступ».

    2. Он реализует отдельный технический функционал. Например: работа с БД, логирование, кэширование.

    3. Он изменяется независимо от остального функционала. Принцип «компонент — единица изменения».

    4. Он может быть повторно использован. Например: единое правило валидации.

    5. У него чёткий API/интерфейс. Контроллеры, сервисы, адаптеры.

    1.11.4. Типы компонентов в архитектуре (C4 Component Tier)

    Компоненты делятся по назначению.

    1.11.4.1. Контроллеры (Controllers)

    Обрабатывают внешние запросы: HTTP, gRPC, WebSocket. Примеры:

    • AuthController;
    • OrderController.

    1.11.4.2. Сервисы бизнес-логики (Business Services)

    Содержат доменные правила. Примеры:

    • OrderService;
    • PricingService;
    • InventoryService.

    1.11.4.3. Репозитории (Repositories)

    Инкапсулируют работу с данными. Примеры:

    • UserRepository;
    • ProductRepository.

    1.11.4.4. Адаптеры внешних систем (Adapters / Gateways)

    Обеспечивают связь с внешними API. Примеры:

    • CRMAdapter;
    • PaymentGatewayClient.

    1.11.4.5. Провайдеры инфраструктуры (Providers)

    Технические сервисы:

    • Logger;
    • CacheProvider;
    • EncryptionProvider.

    1.11.4.6. Компоненты событий (Event Components)

    • EventPublisher;
    • EventConsumer;
    • EventHandler.

    1.11.8. Методика разработки компонентных диаграмм C4

    1. Определи контейнер (API, сервис, приложение, БД).
    2. Выпиши основные функции контейнера.
    3. Раздели их на контроллеры, сервисы, репозитории, адаптеры.
    4. Определи связи: кто кого вызывает.

    5. Проверь, что каждый компонент:

    6. имеет одну ответственность (SRP);

    7. изолирован;
    8. использует чёткие интерфейсы.
    9. Нарисуй диаграмму в стиле C4Component.

    2. Задание

    2.0. Исходные данные (предметная область)

    Для выполнения лабораторной работы используется информационная система по предметной области, закреплённой за студентом на семестр. Конкретный вариант предметной области и функциональных сценариев определяется индивидуальным заданием, опубликованным в ЛМС. Предметная область должна быть согласована с ранее выполненными лабораторными работами.

    2.1. Описание задания

    1. Проанализировать предметную область разрабатываемой информационной системы.
    2. Определить пользователей (акторов), внешние системы и контекст функционирования.
    3. Сформировать архитектурное видение системы в виде набора диаграмм C4.

    4. Построить диаграммы уровней:

    5. C4 Level 1 — Context Diagram

    6. C4 Level 2 — Container Diagram
    7. C4 Level 3 — Component Diagram
    8. (опционально) C4 Level 4 — Code Diagram
    9. Описать обнаруженные компоненты: контроллеры, сервисы, репозитории, адаптеры.
    10. Оформить архитектурный документ с построенными диаграммами.

    2.2. Порядок выполнения работы

    Шаг 1. Анализ контекста и определение акторов

    Определить:

    • кто взаимодействует с системой (пользователи, администраторы, внешние системы);
    • основные сценарии использования.

    Результат: диаграмма C4 Context.

    Шаг 2. Определение контейнеров системы

    Определить крупные блоки архитектуры:

    • Web-интерфейс
    • Backend API
    • База данных
    • Очередь сообщений
    • Внешние интеграции

    Результат: диаграмма C4 Container.

    Шаг 3. Выделение и описание архитектурных компонентов

    На основе структуры контейнеров:

    • выделить контроллеры;
    • выделить сервисы бизнес-логики;
    • определить репозитории;
    • определить адаптеры внешних систем;
    • описать события (если система событийная).

    Результат: текстовое описание компонентов.

    Шаг 4. Построение диаграммы компонентов

    Для выбранного контейнера (обычно Backend API):

    • построить диаграмму C4 Component,
    • показать связи между компонентами (Controller → Service → Repository).

    Если проект микросервисный — построить компонентные диаграммы для каждого сервиса.

    Шаг 5. (Опционально) Диаграмма уровня кода

    Построить C4 Code Diagram для ключевой сущности (например, Order или User).

    Шаг 6. Формирование архитектурного документа

    Финальный отчёт должен содержать:

    1. Описание системы.

    2. Диаграммы:

    3. Context

    4. Container
    5. Component

    6. (опционально) Code

    7. Текстовые описания акторов, контейнеров и компонентов.

    8. Пример сценария взаимодействия (Sequence Diagram или текстовый сценарий).

    2.3. Для выполнения требуется

    1. Шаблон отчёта, указанный в описании лабораторной работы.
    2. Вариант задания, закреплённый за студентом на семестр и опубликованный в ЛМС.
    3. Требования к оформлению — согласно методическим указаниям в ЛМС или соответствующему разделу документации.
    4. Для построения диаграмм использовать draw.io (diagrams.net).

    Все диаграммы должны быть сохранены и вставлены в отчёт в виде изображений с подписями.

    2.4. Запрет

    ❗ Запрещается использование систем искусственного интеллекта для выполнения лабораторной работы.

    Работы, выполненные с использованием ИИ, полностью или частично скопированные, а также не сданные, оцениваются в 0 баллов без возможности доработки.
