# Лабораторная работа №3 - Построение архитектуры программного средства

## **1. Теория**

### **1.0. Цель работы**
Целью лабораторной работы является освоение принципов архитектурного проектирования программного средства с использованием модели C4, включая формирование контекстного, контейнерного и компонентного представлений системы, определение границ ответственности, способов взаимодействия компонентов и обоснование выбранных архитектурных решений.

### **1.1.  Понятие архитектуры программного средства**

**Архитектура программного средства (ПС)** — это совокупность структурных решений о компонентах системы, связях между ними, принципах организации, паттернах взаимодействия и ограничениях, определяющих её качество, расширяемость, эффективность и жизненный цикл.

Архитектура определяет:

* **Что** делает система (функциональные требования).
* **Как** она должна работать (нефункциональные требования: производительность, надёжность, безопасность, масштабируемость).
* **Какие элементы и модули** должны существовать в системе.
* **Каким образом** эти элементы взаимодействуют.

Архитектор фиксирует ключевые решения в виде:

* архитектурных стилей,
* диаграмм,
* ограничений,
* документированных компромиссов.

```mermaid
C4Context
title Контекстная диаграмма программного средства

Person(user, "Пользователь", "Использует систему для выполнения целевых задач")

System_Boundary(sys, "Программное средство") {

}

System_Ext(ext1, "Внешняя система A", "Обменивается данными через API")
System_Ext(ext2, "Внешняя система B", "Источник или потребитель информации")

Rel(user, system, "Взаимодействует через UI/клиент")
Rel(system, ext1, "Запросы / ответы по REST API")
Rel(system, ext2, "Получение или отправка данных")

```

### **1.2. Цели построения архитектуры**

Построение архитектуры направлено на:

1. **Удовлетворение требований** — создание структуры, способной обеспечить выполнение всех функциональных и нефункциональных требований.
2. **Управление сложностью** — разделение системы на управляемые компоненты.
3. **Повышение устойчивости системы (robustness)** — обеспечение отказоустойчивости и предсказуемости.
4. **Масштабируемость** — возможность развития ПС без полного переписывания.
5. **Минимизация рисков** — выявление архитектурных слабостей до начала разработки.
6. **Оптимизацию стоимости владения (TCO)** — снижение затрат на поддержку и развитие.

### **1.3. Компоненты архитектуры программного средства**

#### **1.3.5. Интеграционная архитектура**

Описывает взаимодействие между компонентами и внешними системами.

Может включать:

* события и подписчики (event-driven),

Фиксирует:

* модели доступа (RBAC/ABAC),
* аутентификацию и авторизацию (OAuth2, JWT),
* протоколы шифрования (TLS),
* защиту данных и логирование.
 

#### **1.3.7. Архитектура эксплуатации (DevOps)**

Формирует требования и решения по:

* CI/CD pipeline,
* сборке и доставке артефактов,
* мониторингу и логированию,
* контейнеризации,
* оркестрации (Kubernetes, Docker Swarm).

 
### **1.4. Архитектурные стили**

#### **1.4.1. Монолитная архитектура**

Единый исполняемый модуль, содержащий все компоненты.

Преимущества:

* простота разработки;
* единое деплоивание.

Недостатки:

* сложность масштабирования;
* ограниченная гибкость.

```mermaid
graph TB
    M[Монолитное приложение]
    M --> UI
    M --> Services
    M --> Data
```

## 1.11. Создание диаграммы C4

### 1.11.1. Общие сведения о C4 Model

**C4 Model** — это современный стандарт визуального описания архитектуры программного обеспечения, предложенный Саймоном Брауном.
Название C4 означает четыре уровня абстракции:

1. **Context (Контекст)** — кто взаимодействует с системой и в каком окружении она существует.
2. **Container (Контейнеры)** — крупные участки системы: приложения, API, БД, очереди сообщений.
3. **Component (Компоненты)** — внутренние части контейнеров: сервисы, модули, классы бизнес-логики.
4. **Code (Код/классы)** — отдельные классы и структуры (используется редко).

C4 позволяет:

* описывать архитектуру сверху вниз;
* фиксировать ответственность каждого элемента;
* показывать структурные связи;
* документировать систему независимо от конкретных технологий.


### 1.11.2. Что такое компонент в C4

**Компонент** в C4-модели — это логически обособленная часть контейнера, отвечающая за конкретный кусок функциональности.

Это **не класс** и не исходный файл, а **архитектурная единица**, объединяющая:

* ответственность (responsibility);
* функциональность (capability);
* интерфейсы (API/методы);
* взаимодействие с другими компонентами;
* зависимость от репозиториев, адаптеров, внешних сервисов и т. д.

**Примеры компонентов:**

* `OrderController`, `AuthController`;
* `PaymentService`, `NotificationService`;
* `UserRepository`, `ProductRepository`;
* `EncryptionProvider`;
* `ExternalCRMAdapter`;
* `EventPublisher`.

### 1.11.3. Основной принцип выделения компонентов

Компонент должен быть выделен, если:

1. **Он выполняет уникальную бизнес-роль.**
   Например: «Создать заказ», «Рассчитать тариф», «Проверить доступ».

2. **Он реализует отдельный технический функционал.**
   Например: работа с БД, логирование, кэширование.

3. **Он изменяется независимо от остального функционала.**
   Принцип «компонент — единица изменения».

4. **Он может быть повторно использован.**
   Например: единое правило валидации.

5. **У него чёткий API/интерфейс.**
   Контроллеры, сервисы, адаптеры.



### 1.11.4. Типы компонентов в архитектуре (C4 Component Tier)

Компоненты делятся по назначению.

#### 1.11.4.1. Контроллеры (Controllers)

Обрабатывают внешние запросы: HTTP, gRPC, WebSocket.
Примеры:

* `AuthController`;
* `OrderController`.

#### 1.11.4.2. Сервисы бизнес-логики (Business Services)

Содержат доменные правила.
Примеры:

* `OrderService`;
* `PricingService`;
* `InventoryService`.

#### 1.11.4.3. Репозитории (Repositories)

Инкапсулируют работу с данными.
Примеры:

* `UserRepository`;
* `ProductRepository`.

#### 1.11.4.4. Адаптеры внешних систем (Adapters / Gateways)

Обеспечивают связь с внешними API.
Примеры:

* `CRMAdapter`;
* `PaymentGatewayClient`.

#### 1.11.4.5. Провайдеры инфраструктуры (Providers)

Технические сервисы:

* `Logger`;
* `CacheProvider`;
* `EncryptionProvider`.

#### 1.11.4.6. Компоненты событий (Event Components)

* `EventPublisher`;
* `EventConsumer`;
* `EventHandler`.



### 1.11.5. Общая структура компонентного уровня C4

Типовой набор компонентов:

```text
Backend API Container
 ├─ Controllers
 │    ├─ OrderController
 │    ├─ AuthController
 │    └─ ReportController
 │
 ├─ Services
 │    ├─ OrderService
 │    ├─ PaymentService
 │    └─ NotificationService

 │    ├─ UserRepository
 │    ├─ ProductRepository
 │    └─ OrderRepository

 ├─ Adapters
 │    ├─ CRMAdapter
 │    └─ PaymentGateway
 │
 └─ Infrastructure
      ├─ LoggingProvider
      ├─ CacheProvider
      └─ EventPublisher
```

### 1.11.8. Методика разработки компонентных диаграмм C4

1. Определи **контейнер** (API, сервис, приложение, БД).
2. Выпиши **основные функции** контейнера.
3. Раздели их на **контроллеры**, **сервисы**, **репозитории**, **адаптеры**.
4. Определи связи: кто кого вызывает.
5. Проверь, что каждый компонент:

   * имеет одну ответственность (SRP);
   * изолирован;
   * использует чёткие интерфейсы.
6. Нарисуй диаграмму в стиле `C4Component`.



### 1.11.9. Уровни C4 с примерами и отдельными диаграммами

#### 1.11.9.1. Level 1 — Context Diagram

Диаграмма контекста показывает:

* систему как чёрный ящик;
* пользователей (акторов);
* внешние системы;
* основные взаимодействия.

**Пример контекстной диаграммы (C4Context):**

```mermaid
C4Context
title C4 — Диаграмма контекста

Person(user, "Пользователь", "Использует систему для выполнения операций")
System_Boundary(sys, "Информационная система") {
    System(app, "Основное приложение", "Предоставляет основной функционал")
}

System_Ext(ext1, "CRM", "Внешняя система управления клиентами")
System_Ext(ext2, "Платежный сервис", "Обрабатывает транзакции")

Rel(user, app, "Взаимодействует через интерфейс")
Rel(app, ext1, "Обменивается клиентскими данными")
Rel(app, ext2, "Запрашивает проведение платежей")
```

#### 1.11.9.2. Level 2 — Container Diagram

Контейнер — это **крупный исполняемый модуль**: web-приложение, мобильное приложение, API, база данных, брокер сообщений.
Контейнеры внутри системы взаимодействуют друг с другом и формируют архитектуру высокого уровня.

**Пример C4Container:**

```mermaid
C4Container
title C4 — Диаграмма контейнеров

Person(user, "Пользователь")

System_Boundary(sys, "Информационная система") {

    Container(ui, "Web UI", "React / Angular / Vue", "Предоставляет пользовательский интерфейс")
    Container(api, "Backend API", "Node.js / .NET / FastAPI", "Реализует бизнес-логику")
    Container(db, "Database", "PostgreSQL", "Хранит данные")
    ContainerQueue(mq, "Message Queue", "RabbitMQ", "Асинхронные события и интеграции")
}

Rel(user, ui, "Использует")
Rel(ui, api, "HTTP/HTTPS")
Rel(api, db, "SQL")
Rel(api, mq, "Публикует события")
Rel(mq, api, "Асинхронные уведомления")
```

### 1.11.10. Дополнительные рекомендации по построению диаграмм C4

1. Определи **окружение системы**:
   кто пользователи, какие внешние системы.

   база данных, API, фронтенд, сервисы, брокер сообщений.

3. Для каждого контейнера выдели **компоненты**:
   сервисы, репозитории, контроллеры, адаптеры.

4. При необходимости проработай **уровень кода (классы)**.

5. Используй **единый стиль и нотацию**:
   названия, описания, формулировки связей.

## **2. Задание**

### **2.0. Исходные данные (предметная область)**
Для выполнения лабораторной работы используется информационная система по предметной области, закреплённой за студентом на семестр.
Конкретный вариант предметной области и функциональных сценариев определяется индивидуальным заданием, опубликованным в ЛМС.
Предметная область должна быть согласована с ранее выполненными лабораторными работами. 

###  **2.1. Описание задания**
1. Проанализировать предметную область разрабатываемой информационной системы.
2. Определить пользователей (акторов), внешние системы и контекст функционирования.
3. Сформировать архитектурное видение системы в виде набора диаграмм C4.
4. Построить диаграммы уровней:

   * **C4 Level 1 — Context Diagram**
   * **C4 Level 2 — Container Diagram**
   * **C4 Level 3 — Component Diagram**
   * (опционально) **C4 Level 4 — Code Diagram**
5. Описать обнаруженные компоненты: контроллеры, сервисы, репозитории, адаптеры.
6. Оформить архитектурный документ с построенными диаграммами.


### **2.2. Порядок выполнения работы**

#### **Шаг 1. Анализ контекста и определение акторов**

Определить:

* кто взаимодействует с системой (пользователи, администраторы, внешние системы);
* основные сценарии использования.

**Результат:** диаграмма **C4 Context**.

#### **Шаг 2. Определение контейнеров системы**

Определить крупные блоки архитектуры:

* Web-интерфейс
* Backend API
* База данных
* Очередь сообщений
* Внешние интеграции

**Результат:** диаграмма **C4 Container**.

#### **Шаг 3. Выделение и описание архитектурных компонентов**

На основе структуры контейнеров:

* выделить контроллеры;
* выделить сервисы бизнес-логики;
* определить репозитории;
* определить адаптеры внешних систем;
* описать события (если система событийная).

**Результат:** текстовое описание компонентов.

#### **Шаг 4. Построение диаграммы компонентов**

Для выбранного контейнера (обычно Backend API):

* построить диаграмму **C4 Component**,
* показать связи между компонентами (Controller → Service → Repository).

Если проект микросервисный — построить компонентные диаграммы для каждого сервиса.

#### **Шаг 5. (Опционально) Диаграмма уровня кода**

Построить **C4 Code Diagram** для ключевой сущности (например, Order или User).

#### **Шаг 6. Формирование архитектурного документа**

Финальный отчёт должен содержать:

1. Описание системы.

2. Диаграммы:

   * Context
   * Container
   * Component
   * (опционально) Code

3. Текстовые описания акторов, контейнеров и компонентов.

4. Пример сценария взаимодействия (Sequence Diagram или текстовый сценарий).


### **2.3. Для выполнения требуется**

1. **Шаблон отчёта**, указанный в описании лабораторной работы.
2. **Вариант задания**, закреплённый за студентом на семестр и опубликованный в ЛМС.
3. **Требования к оформлению** — согласно методическим указаниям в ЛМС или соответствующему разделу документации.
4. Для построения диаграмм использовать **draw.io (diagrams.net)**.

Все диаграммы должны быть сохранены и вставлены в отчёт в виде изображений с подписями.


### **2.4. Запрет**

❗ **Запрещается использование систем искусственного интеллекта для выполнения лабораторной работы.**
